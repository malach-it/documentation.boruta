Boruta 0.14.0 scopes browser sessions by authorization client, improves consent handling for identity and credential presentation flows, and adds WebAuthn and TOTP activity logging. It also fixes template updates, backend metadata defaults, and credential configuration persistence.

:::note Open beta

Boruta is currently in an open beta phase. While it is mostly stable and parts of the project have undergone security assessments, it remains a work in progress. We encourage you to test Boruta in your own context and share feedback: production readiness depends on real-world use to uncover bugs and improve usability. Please also review the [General Terms and Conditions](https://github.com/malach-it/boruta-server/blob/master/GENERAL_TERMS_AND_CONDITIONS.md).

:::

<!--truncate-->

## Client sessions and request handling

Browser sessions are now scoped by the requested authorization client ID, enabling concurrent sessions for different clients. **Upgrading resets all active browser sessions**, so users will need to sign in again.

Identity providers now offer a choice between stateless request mode, which remains the default, and stateful request mode. Stateful mode stores the signed request JWT in the session cookie and omits it from initial identity-route URLs.

:::warning Stateful request mode

Do not enable stateful mode until login and other identity steps are bound to individual requests. The consent protection described below does not remove this limitation.

:::

Stateful consent forms now submit an opaque request ID and reject missing or replaced requests. This prevents an earlier consent form from granting consent to a different client. Consent requests without a scope also no longer produce an internal server error.

## Credential presentation and machine-user consent

The `vp_token` response type now requires resource owner or machine authentication. Machine users can grant consent for OID4VP requests using their verified DID as the client identity.

Machine-user sessions are bound to the originating authorization code and DID. Unrelated authorization requests clear the machine session, preventing it from being reused across unrelated flows. Public-client preauthorization also resumes with the expected response types.

## Administration and activity logging

User edit pages now show saved consents, including client IDs, scopes, and update times. WebAuthn and TOTP registration and authentication emit success and failure events, and successful authorization and token issuance logs include the authorized scope.

Template administration is more reliable: resetting a template immediately refreshes the text editor with the default content, and identity provider template updates invalidate cached content even when the update omits the template type. User edit forms also retain their values after an update fails.

## Backend and credential fixes

Backend metadata defaults now persist from the administration form and populate issued credential claims when a user has no value. Verifiable credential claim status TTL settings also persist from the backend form.

The authorization database now enforces uniqueness for public client IDs.

## Before upgrading

Boruta remains in beta during the `0.x` series, so releases may include breaking changes. Plan for users to sign in again after the session reset, and check that credential presentation integrations authenticate a resource owner or machine user before requesting `vp_token`.

Keep identity providers in the default stateless request mode until the request-binding limitation above is resolved. Review existing public client IDs for duplicates before applying the new uniqueness constraint.
